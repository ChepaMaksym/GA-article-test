# Частина 3: розмір популяції

Модуль готує дослідження сталої популяції для рюкзаків на 100, 200 і 500 предметів. Правила та майбутні порівняння зафіксовано в `PROTOCOL_UK.md`. Вибраних популяцій і нових емпіричних результатів ще немає.

## Програмні складові

- `presentation_package/program/ga_core/` містить єдиний активний цикл ГА. Новий необов’язковий аргумент `initial_parameters` задає сталу конфігурацію. Старі виклики без аргументу зберігають умови та формат журналів.
- `inputs.py` перевіряє походження задач і створює спільні початкові банки.
- `exact.py` обчислює точні еталони двома незалежними способами динамічного програмування.
- `execution.py` виконує тільки 18 зареєстрованих технічних запусків.
- `verification.py` незалежно відновлює оператори, генератори та популяції за журналом.
- `observations.py` відокремлює шкалу загальних оцінювань, початкову фазу, завершені покоління та неповний блок.
- `costs.py` оцінює окремі варіанти кошторису за виміряними витратами пілота. Прогноз не є доведеним максимумом витрат і не надає дозволу наступній серії.
- `mathematics.py` і `figures.py` готують формули та теоретичні рисунки. Рисунки не є результатами ГА.
- `driver.py` з’єднує дозволені фази CI; `authority.py` перевіряє окремий дозвіл і сукупні витрати.

Пошукове ядро не отримує OPT. Початкові оцінки перевіряються повторно, але логічно початок зараховується один раз. Ці фізичні перевірні витрати відображаються окремо.

## Технічна послідовність

Усі числові дії виконуються тільки в GitHub Actions. Локального запуску тестів або пошуку для цього дослідження не передбачено.

1. Окремо погодити ресурсну стелю й зафіксувати відповідь у `resource_authorization.json`. За відсутності дозволу робочий процес зупиняється.
2. Фаза `tests`: виконати програмні перевірки, відтворити історичний еталон і побудувати два теоретичні рисунки.
3. Після успішного завершення зберегти квитанцію `frozen_tests.json` із походженням і контрольними сумами артефакту.
4. Фаза `prepare-pilot`: перевірити сирі байти дев’яти задач, отримати два точні еталони та підготувати дев’ять спільних банків. Зберегти квитанцію `frozen_pilot.json`.
5. Фаза `pilot`: дев’ять завдань виконують по два запуски для популяцій 2 та 25 000. Одночасно працює не більше чотирьох завдань. Невдале завдання зберігає свій стан; заміни іншим seed немає.
6. Підсумок перевіряє повноту 18 запусків і зберігає виміряні витрати. Лише після цього готуються кошториси налаштування irace та основної серії.

Кожна квитанція містить `status: VERIFIED`, `phase`, `run_id`, `run_attempt`, `artifact_id`, `artifact_name`, `source_manifest_sha256`, `archive_sha256`, `file_manifest_sha256` і `report_sha256`. Для тестів звітом є `software_tests.json`, для початків `registry.json`. Після фіксації квитанції дозволено змінювати лише файли квитанцій та обліку ресурсів. Зміна наукового коду потребує повторної програмної перевірки й обліку додаткових витрат.

У робочому процесі є три фази: `tests`, `prepare-pilot`, `pilot`. Звичайне надсилання коміту не запускає їх. На дослідницькій гілці фазу задає одна явна позначка в повідомленні коміту: `[population-size:tests]`, `[population-size:prepare-pilot]` або `[population-size:pilot]`. Кожний запуск додатково перевіряє дозвіл. Довільного вибору задач, seed або популяцій через робочий процес немає.

## Межі готовності

Підготовлений виконавець не запускає irace або остаточні 8100 запусків. Число перевірок, повторень налаштування, версії R та залежностей фіксуються після технічного пілота, до відкриття незалежних результатів. Готовність коду не означає завершення дослідження.

Методичний документ Word/PDF зберігається окремо в `Магістерська_рюкзак/Частина_3/`. Частину 2 та її результати не перезаписують.
